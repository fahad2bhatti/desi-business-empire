# Delivery Phases
No calendar commitments are implied. Estimate after Phase 0; exit based on evidence, not elapsed time.

## Phase 0 — Define and validate (F01–F03)
Approve starter route, audience, launch platform order, wireframes and economy model. Resolve whether the founder wants an active simulation or mostly idle pacing. Exit: playable rules on paper and an approved first-sale-to-upgrade flow.

## Phase 1 — First playable (F04–F11)
Build wallet, config, SQLite saves, stall loop, basic upgrades, takeaway transition and onboarding. No ads, purchases or login. Exit: a new user can make a sale, upgrade, restart and resume correctly; core arithmetic and recovery tests pass.

## Phase 2 — Food MVP (F12–F18)
Add staffing, capped offline simulation, restaurant/hall progression, goals, accessibility, settings and observed playtests. Exit: full route playable without purchases; lifecycle/save-loss tests and named-device performance review complete. Decide whether this becomes a free public beta or needs more private testing.

## Phase 3 — Optional commercial services (F19–F22)
Approve authority/security design, implement verified purchases and optional rewarded ads only if chosen. Check current platform policies at implementation time. Exit: replay/refund/restore/no-fill/consent tests and store disclosures approved. A non-monetized launch can skip this phase; no paid service launches with unfinished verification.

## Phase 4 — Expansion (F23–F25)
Choose second branch based on playtest/user evidence. Add cloud sync only with an approved conflict policy. Introduce connected supply bonuses after independent branches work. Exit: every addition has migration, balance and dependency tests.

## Release blockers
Critical save corruption; negative currency or inventory; duplicate offline grants; unverified paid grants; unauthorized cloud access; missing privacy/audience decisions; misleading real-money claims. Do not bypass blockers to hit a date.
